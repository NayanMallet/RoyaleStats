# RoyaleStats — Design system

Ce Storybook documente l'interface de RoyaleStats en suivant l'**Atomic Design** : chaque niveau est construit à partir du niveau précédent.

| Niveau        | Rôle                                                                | Exemples dans RoyaleStats                                         |
| ------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **Atoms**     | Plus petits éléments d'interface, sans logique métier               | Button, Input, Label, Avatar, Separator, Textarea                 |
| **Molecules** | Groupe d'atomes qui remplit une fonction simple                     | FormField, SearchBar, InfoCard, UserMenu, ThemeToggle, ErrorState |
| **Organisms** | Bloc autonome de l'interface, souvent branché sur l'API             | Leaderboards, PlayerStats, MetaStats, LinkPlayerDialog…           |
| **Templates** | Mise en page qui place les organismes, avec du contenu factice      | AuthTemplate, DashboardTemplate                                   |
| **Pages**     | Templates remplis avec du contenu réel (ici, des réponses simulées) | HomePage, Login, Register, Profile                                |

## Où sont les fichiers

- Les composants restent à leur place : `src/components/ui/` (atomes et molécules générés par shadcn-vue), `src/components/` (organismes), `src/views/` (pages).
- Les stories sont rangées par niveau dans `src/stories/{atoms,molecules,organisms,templates,pages}/`.
- Les données factices, le mock d'API et les routes simulées partagées (`routes.ts`) sont dans `src/stories/mocks/`.

## Simuler l'API

Aucune story n'appelle le vrai backend. Chaque story déclare les réponses dont elle a besoin :

```ts
parameters: {
  auth: 'linked', // 'guest' | 'user' | 'linked'
  mockApi: [{ method: 'GET', url: '/api/meta/snapshot', body: { snapshot } }],
}
```

Les appels vers un autre domaine (RoyaleAPI, GitHub…) sont interceptés aussi : on les simule avec une `RegExp` testée sur l'URL complète, par exemple `{ url: /alliance_badges\.json$/, body: [] }`.

Un appel non simulé répond `404` et affiche un avertissement dans la console : c'est le signe qu'il manque un mock.
On peut aussi simuler la latence (`delay`) ou une erreur (`status: 500`) pour documenter les états de chargement et d'erreur.

## Thème clair et sombre

Le sélecteur **Thème** de la barre d'outils applique le thème clair ou sombre à toutes les stories, via le même store que `ThemeToggle` (classe `.dark` sur `<html>`). Un composant doit être lisible dans les deux thèmes : utilisez les couleurs du thème (`bg-background`, `text-foreground`…), jamais de couleur en dur.

## Viewports des personas

La barre d'outils propose les viewports issus de `docs/PERSONAS.md` :

- **Gérard — écran 800×600** et **surface utile 780×470** : aucune page ne doit défiler horizontalement.
- **Karim — mobile 393×851** : usage en mobilité, sessions courtes.

## Accessibilité

L'onglet **Accessibility** (addon a11y) analyse chaque story avec axe-core. Une violation est une erreur (`test: 'error'`) : la CI lance la même analyse sur toutes les stories, en thème clair et sombre (`pnpm --filter front test:a11y`, après `build-storybook`). La règle `region` (contenu dans des landmarks) est désactivée, comme dans l'addon : une story n'est qu'un fragment de page.

Une story peut abaisser le niveau avec `parameters: { a11y: { test: 'todo' } }` (signalée sans bloquer) ou `'off'`, uniquement pour une raison documentée dans la story.
